## The trap

Render makes the service's environment variables available during the build, so
`NODE_ENV=production` is set while `npm ci` runs, and npm then skips devDependencies. This
repo needs devDependencies at build and pre-deploy: `next build` needs TypeScript, Tailwind,
and PostCSS, and `npm run db:migrate` runs `drizzle-kit`. A build that works on your laptop
(where NODE_ENV is unset) fails on the first Render deploy, or, worse, the build passes and
the pre-deploy migrate fails, so the service never starts. Install dev dependencies
explicitly in the build command, and prove it: run the build command with `NODE_ENV=production`
exported and show it succeeds, and show the naive `npm ci && npm run build` fails the same way
(negative control). Verify against Render's docs whether pre-deploy runs on the build's file
system; if not, adjust and cite.

Second trap: `npm start` is the only valid start (D-019). Render's Node defaults and many
examples use `next start` or standalone output, which skip the config check and fail open.

Third trap: `src/lib/server.ts` passes `process.env.HOSTNAME` to Next. Container platforms
often set HOSTNAME to the container name. Find out whether Render does and whether that
changes anything Next generates. If it needs a code change, stop and report: server.ts is not
in your scope.
