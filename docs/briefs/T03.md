## The trap

The activation link is a bearer credential that makes someone the owner of an organization.
Getting it wrong in either of two ways gives an organization to the wrong person:
(a) consumption that reads `used_at is null` and then updates in a separate statement lets two
concurrent requests both succeed. Use one conditional UPDATE … RETURNING (or a row lock) and
test it with two truly concurrent consumers. (b) A link not bound to the invited, verified
email becomes transferable: anyone who sees it in a chat log owns the org. A test must show a
different verified user cannot consume it, and an unverified user with the right email cannot
either.

Second trap: `withOrgBootstrapTx` sets `app.org_id` without checking anything. It is the
right tool for admin operations only because your helper re-checks `site_admins` inside the
same transaction. If that check is outside the transaction or keyed on the principal's
`siteAdmin` claim, a stale or forged principal becomes an admin.

Third trap: the existing Playwright config starts the production server (`NODE_ENV=production`).
Once `RESEND_API_KEY` and `EMAIL_FROM` are required in production, e2e must supply values.
Do not add any env-validation skip switch (T01 forbade one). Give e2e syntactically valid
placeholder values, seed verified users directly in its throwaway database, and cover the
email content (verification and reset links) in integration tests with the capturing adapter.
If you change playwright.config.ts, declare it.

## Coverage (properties; integration tests against real Postgres as the non-superuser role the harness provides)

- Two concurrent consumers of one activation link: exactly one becomes owner; the other gets
  a clear error. A second consume after success fails. An expired link fails.
- A different verified user, and an unverified user with the invited email, cannot consume.
- `owner_activations` holds only the hash; no test can find the raw token in the table.
- A non-admin calling every admin operation gets `forbidden_or_not_found` and nothing is
  written; deleting the `site_admins` row makes the next admin call fail even when the
  principal still says `siteAdmin: true`.
- After `suspendOrganization`, the owner's next `withOrgTx` throws `org_suspended`, and so
  does an agent principal for that org (seed a token row directly). After restore, both work.
- Each admin operation writes exactly one audit row in the target org, with the admin's
  user id as actor and no secret in before/after.
- A user who already owns an org cannot be associated with a second (D-005).
- `getHumanPrincipal`: unverified user → null; owner → orgId set; a user whose org is
  another user's → no orgId; site admin flag tracks the table on each call.
- Verification and reset emails are delivered to the capturing adapter with a working link.
- e2e (Chromium): sign in as a seeded owner; admin creates an org and sees it listed; a
  non-admin opening `/admin` gets 404; a suspended owner lands on the suspended page.
