## The trap

Three ways to get this wrong, each of which passes a casual look:

1. **A global `"esbuild": "^0.25.0"` override.** On 0.x, `^0.25.0` means `>=0.25.0 <0.26.0`, so it
   would also force tsx and vite from 0.28.2 down to 0.25.x. tsx runs `npm start` in production and
   vite runs every unit test; a silent esbuild downgrade under them is exactly the kind of change
   this task must not make. Scope the override under `@esbuild-kit/core-utils`; tsx, vite and
   drizzle-kit's own esbuild must keep the versions shown above.
2. **`npm audit fix --force`.** Its suggested fix is drizzle-kit 0.18.1 — a downgrade of several
   major versions that would break `db:generate`/`db:migrate`. Do not run `npm audit fix` in any form.
3. **Regenerating the lockfile** (`rm package-lock.json && npm install`, or `npm update`). That floats
   every dependency. The lockfile diff must be limited to the `@esbuild-kit/core-utils` esbuild
   entry (removal or replacement of `node_modules/@esbuild-kit/core-utils/node_modules/esbuild` and
   its platform packages). Report `git diff --stat package-lock.json` and explain every changed
   package path in the PR body.
