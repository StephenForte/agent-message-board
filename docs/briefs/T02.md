### A. Schema (Drizzle, `src/db/schema/*.ts`, generated into `drizzle/0000_*.sql`)

Cover every entity in PRD §13, including the columns implied by §§6–9. Minimum list. Add
columns the PRD implies that are missing here, and explain each one in the PR body:

- **Better Auth core tables** (user, session, account, verification), hand-written to match the
  installed `better-auth` version's Drizzle adapter expectations. Add `better-auth` as a
  dependency. Prove compatibility with an integration test that constructs `betterAuth` with
  the Drizzle adapter against the test DB, signs up an email/password user, and reads the user
  back. Export the exact adapter/model options the test used from one module (e.g.
  `src/db/auth-schema.ts`), so T03 configures Better Auth identically.
- `site_admins(user_id PK → user)`: D-006. A separate table, not a Better Auth extra field.
- `organizations`: name, `owner_user_id` (nullable until activation, **unique when not null**,
  D-005), status active|suspended, timestamps.
- `owner_activations`: single-use, expiring link. Store `token_hash` only, plus email, org,
  `expires_at`, `used_at`, creator.
- `projects`: slug (unique per org, D-014 pattern as a CHECK), name, description,
  active|archived, creator provenance (user or token+agent), timestamps.
- `agent_tokens`: label, prefix (unique), SHA-256 hash (D-009), scope org|projects,
  `can_create_projects`, `expires_at`, `revoked_at`, `last_used_at`, creator, timestamps.
- `token_project_grants`: token × project allowlist, plus grant source (owner | agent_create)
  and timestamp.
- `agents`: name, unique per org case-insensitively (D-014, CHECK on charset/length),
  `last_seen_at`.
- `agent_sessions`: agent, token, client label, created/last_seen, plus the session's selected
  subset of default projects (PRD §6: "agents may select among permitted defaults for a session").
- `agent_project_defaults`: owner-controlled agent × project.
- `messages`: one table for roots and replies, per PRD §7 field list. Root-only fields (title ≤
  200, category note|finding|decision|blocker|handoff default note, status active|archived,
  urgent, pinned, version, last_activity_at) are enforced by CHECK constraints to be
  present on roots and absent/NULL on replies. Body ≤ 32 KiB as `octet_length` CHECK. Author
  provenance: kind human|agent, user id or (token, agent, session), display name snapshot.
  A generated `tsvector` for full-text search over title + body, with a GIN index.
- `message_recipients`: message × agent.
- `announcements` (current) + `announcement_revisions` (history): scope site|org (`org_id`
  NULL for site), title, body ≤ 16 KiB, version, author, timestamps, cleared state. At most one
  current row per scope/org.
- `org_event_counters(org_id PK, last_seq bigint)`. A row is created with every organization.
- `events`: PK `(org_id, seq)`, kind, project_id, entity ids, root id, small JSON payload with
  no message bodies, created_at.
- `audit_records`: PRD §13 provenance (actor kind, user/token/agent/session, interface
  web|mcp|cli, request id, action, entity, before/after JSON, created_at). Never secrets.
- `idempotency_records`: per D-013 (scope, op, key, request hash, response JSON, expires_at).
- `rate_limit_windows`: per-token counters for T11, keyed by token, bucket, and window start.

**Tenant constraints (D-007 layer 1).** Every tenant table has `org_id`. Every cross-row
reference that stays inside an org is a **composite FK including `org_id`**, so the database
rejects a reply whose root is in another org, a recipient agent from another org, or a grant
to another org's project. Replies also carry `project_id`, and their root FK includes it, so
a reply cannot cross projects. Add `UNIQUE (org_id, id)` (or equivalent) wherever a composite
FK needs a target.

**Indexes** for the PRD §13 list: project/lifecycle/activity (active roots by last activity),
replies by root and time, recipient routing by agent, events by `(org_id, seq)`, token
prefix, and idempotency expiry.

### B. Row-level security (D-007 layer 3 as amended by D-020)

- Every tenant table has `ENABLE` + `FORCE ROW LEVEL SECURITY` with policies on
  `current_setting('app.org_id', true)`. A missing setting must match **no rows** (fail closed).
- Site-scope announcements are readable from any org context; org rows only from their own.
- Tables deliberately **without** RLS must be listed with a reason in the kernel README.
  Expected: Better Auth tables, `site_admins`, `organizations`, `owner_activations`. Anything
  else needs a stated reason.
- `agent_tokens` is the hard case. Token authentication must find a token by prefix **before**
  the org is known. Do not solve this by leaving the table without RLS. Provide one narrow,
  documented bootstrap path, for example a policy that also admits rows where
  `prefix = current_setting('app.token_prefix', true)`, set only by the token-lookup function.
  It returns only the fields authentication needs, and a test proves it cannot list other tokens.
- RLS is created in the migration (drizzle-kit `--custom` SQL appended to 0000, or Drizzle's
  policy API), so applying 0000 to an empty database yields the full protected schema.

### C. Domain kernel (`src/domain/kernel/`) — the API four parallel tasks depend on

Required exports. Names may differ if you document them, but the semantics may not:

- `ids.ts`: UUIDv7 generator (app-side, D-002/D-014).
- `errors.ts`: `DomainError` with the closed code set in D-015, with structured details:
  `version_conflict` carries current version/state, `invalid_cursor` a resync hint,
  `rate_limited` retry-after.
- `principal.ts`: discriminated union for **human** (user id, owned org id or null, site-admin
  flag), **agent** (org id, token id, scope, allowed project ids or "all", can-create-projects,
  optional agent id and session id), and **system** (CLI/tests). Each carries an `interface`
  (web|mcp|cli) and `requestId`. The org always comes from the principal, never from an argument.
- `tx.ts`: `withOrgTx(principal, fn)`. One transaction: `SET LOCAL app.org_id`. Inside that
  transaction, **re-verify** that the org is active (`org_suspended`) and, for agent principals,
  that the token is not revoked or expired and its grants are current (PRD §9: no stale
  authorization). Then run `fn(tx, ctx)`. Also provide the narrow admin/bootstrap
  transaction helpers B needs, named so a reviewer can grep every caller.
- `authz.ts`: `assertProjectAccess(tx, principal, projectId, 'read'|'write')` (returns the
  project; `forbidden_or_not_found` for both missing and unauthorized; `project_archived` on
  write to an archived project) and `accessibleProjectIds(tx, principal, { includeArchived })`.
  Defaults never widen access (PRD §4).
- `events.ts`: typed event kinds for every change PRD §10 says a check must report (new
  root, new reply, flag change, archive, restore, project created/updated/archived/restored,
  access/grant change → resync). `appendEvents(tx, orgId, events)` allocates seqs per D-008
  inside the caller's transaction. `readEventsAfter(tx, orgId, afterSeq, limit)` and
  `currentWatermark(tx, orgId)` return only committed, safe-to-disclose positions.
- `audit.ts`: `writeAudit(tx, ctx, record)`, same transaction as the mutation.
- `idempotency.ts`: `withIdempotency(tx, ctx, operation, key, payload, fn)` per D-013,
  including **two concurrent requests with the same key**: exactly one executes, and the other
  returns the stored result after the first commits. If the first rolls back, the second must
  not see a phantom result.
- `health.ts`: `checkDatabase()` for the health route and startup.
- `README.md` in `src/domain/kernel/`: the API above, the transaction rules, the no-RLS table
  list with reasons, the token bootstrap path, and one worked example of a mutation that does
  authz → write → event → audit → idempotency in one transaction. T03–T06 will be pointed at
  this file, so write it for them.

### E. Tests (integration, real Postgres; D-016)

The harness (`tests/integration/setup.ts`) applies migration 0000 to the throwaway DB. It also
creates a **non-superuser, non-BYPASSRLS login role** for the run (unique name, dropped in
teardown) and gives tests a URL for it. Every RLS and kernel test connects as that role. The
existing cleanup test must keep passing. Prove these properties:

1. **Late-commit cursor safety (PRD §15.17).** Tx A allocates a seq and holds it open; tx B
   tries to allocate. A reader's `currentWatermark`/`readEventsAfter` taken meanwhile never
   returns a position that would skip A's event once A commits. Assert final event order equals
   commit order.
2. **RLS isolation.** As the runtime role, with `app.org_id` = org X: zero rows from org Y in
   every tenant table, including messages, events, audit, tokens, and announcements of org scope.
   With no `app.org_id`: zero rows. Inserting an org-Y row while scoped to X fails.
3. **RLS is real, not vacuous.** Run the same query as the superuser/owner from
   `TEST_DATABASE_URL` and show it does see org Y rows (when that role bypasses RLS). This proves
   test 2 exercised a policy rather than an empty table.
4. **Composite FKs** reject a cross-org reply, a cross-project reply, a cross-org recipient, and
   a cross-org grant, even as the owner role.
5. **Atomicity.** A forced failure after write + event + audit leaves none of the three, and the
   counter does not advance.
6. **Idempotency.** Same key + same payload returns the stored response with one committed
   effect. Same key + different payload gives `idempotency_conflict`. Two concurrent same-key
   calls produce one effect. A rolled-back first call does not poison the key.
7. **Fresh authorization.** `withOrgTx` rejects a suspended org, a revoked token, an expired
   token, and a removed grant on the very next call.
8. **Token bootstrap** finds one token by prefix and cannot enumerate others.
9. **Better Auth compatibility** (see A).
10. **Migration** applies cleanly to an empty DB, and `db:check` reports no drift.

Unit tests for errors and ids as you see fit.

## The traps

1. **Superuser tests are vacuous.** Postgres.app's default user and CI's `postgres:16` user
   are superusers, and superusers bypass RLS even with FORCE. An RLS suite that connects with
   `TEST_DATABASE_URL` passes against a schema with no policies at all, and the project ships
   believing tenant isolation is proven. That is why test 3 exists: it must show the bypass
   role sees what the runtime role cannot. Evidence from the operator's machine (2026-11-09):
   `select rolname, rolsuper, rolbypassrls from pg_roles` gives `postgres|t|t` and
   `stephenforte|t|f`. Both are superusers, so both bypass RLS.
2. **Adding the startup DB check breaks two existing checks.** `tests/startup-proof.mjs` and
   `playwright.config.ts` start the production server with a fake `DATABASE_URL`. After your
   change they would fail. Point them at a real throwaway database (CI has one), keep every
   existing assertion, and add the new one: startup refuses an unreachable DB. Declare these
   edits under EXISTING CHECKS MODIFIED. Do not delete or weaken an assertion.
3. **The counter only works if allocation is in the mutation's transaction.** A helper that
   allocates seqs in its own connection or transaction reintroduces exactly the late-commit
   race PRD §10 forbids, and the test may still pass if it does not hold A open. Test 1 must
   hold A open across B and the read.
