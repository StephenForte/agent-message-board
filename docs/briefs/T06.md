## What must be true when you are done

Module `src/domain/announcements/**` with a README listing its exports. Use these exported
names (argue in DECISIONS NEEDED if one is wrong; do not silently rename):

- `getAnnouncements(principal)` and `getAnnouncementsInTx(tx, ctx)` → `{ site, org }`, each
  null or `{ id, scope, title, body, version, authorDisplayName, authorKind: 'human',
  updatedAt }`. Cleared counts as null. Works for an owner, an org-wide token, and a
  restricted token alike, and reveals nothing about projects. T07 calls the InTx form inside
  its board check; T08 calls the plain form.
- `setOrgAnnouncement(principal, { title, body, expectedVersion })` and
  `clearOrgAnnouncement(principal, { expectedVersion })`: org owner only (inside `withOrgTx`);
  an agent principal gets `capability_denied`. Writes the live row and a revision row in the
  same transaction, plus one audit record in the org.
- `setSiteAnnouncement(principal, { title, body, expectedVersion })` and
  `clearSiteAnnouncement(principal, { expectedVersion })`: inside `withSiteAdminTx`, and the
  acting user's `site_admins` row is re-read in that same transaction (the principal's
  `siteAdmin` flag is a hint, not proof). Non-admin → `forbidden_or_not_found`. Live row and
  revision in one transaction; no audit row (D-023).
- `listAnnouncementRevisions(principal, { scope })`: org history for the owner, site history
  for a site admin, newest first, limit 20 / max 100.
- Versions: the first publish is version 1 with `expectedVersion: 0`; each set or clear adds 1.
  A stale `expectedVersion` → `versionConflict(currentVersion, currentState)` and nothing is
  written. Clearing sets `cleared_at` and writes a revision; never delete rows.
- Limits: title 1–16384 bytes, body ≤ 16384 bytes, measured as UTF-8 bytes →
  `content_too_large`, not a raw CHECK error.
- No event is appended for announcement changes (kernel README: announcement freshness is
  independent of the cursor, PRD §10).

## The trap

The site row is visible from every org context by design (PRD §8), so the read policy is
wide. The write must not be. Two ways it leaks: (1) writing the site announcement inside
`withOrgTx` "because the user is an admin and has an org": the policy then rejects it, and
the tempting fix is to loosen the policy or switch helpers without the re-check. (2) Checking
`principal.siteAdmin` instead of re-reading `site_admins` in the transaction: a principal
built before the admin was removed keeps publishing to every organization on the service. A
test must remove the `site_admins` row and show the next publish fails while the principal
still claims `siteAdmin: true`.

Second trap: two first-time publishes at once. Both see "no row" and both insert; the unique
index rejects one with a raw error. Map it to `version_conflict` (the loser can reload and
retry), and test it with two concurrent calls.

## Coverage (properties; integration tests against real Postgres as the non-superuser role)

- Owner sets the org announcement; an org-wide token and a restricted token in the same org
  both read it and the site one; a token in another org reads the site one and not this org's.
- Agent principals calling any set/clear → `capability_denied`; nothing written.
- Non-admin calling site set/clear → `forbidden_or_not_found`; removing the `site_admins` row
  makes the next publish fail with the principal unchanged.
- Stale `expectedVersion` → `version_conflict` with current version and state; two concurrent
  first publishes → one success, one `version_conflict`.
- Set, set, clear → versions 1, 2, 3; three revisions; `getAnnouncements` returns null for that
  scope after clear; history lists all three.
- Oversize title or body → `content_too_large`.
- Suspended org: owner and agent reads → `org_suspended` (from `withOrgTx`).
- Org announcement changes write exactly one audit row each; site changes write none.

Seed orgs, users, site admins, and tokens directly with SQL in your own fixtures.
