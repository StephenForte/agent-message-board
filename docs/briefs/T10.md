## The trap

The secret must exist in exactly one place, the response that creates it. Next.js makes several
leaks easy, and each one is an incident because the secret is a bearer credential (D-009):
- Putting it in a redirect URL or query string. Route logs redact only `amb_*` patterns, and
  browser history and Referer are not redacted at all.
- Storing it in a cookie, a flash message, `sessionStorage`, or anything that survives the response.
- Returning it from a server action and then calling `revalidatePath` or `redirect`, which re-renders
  a page payload that includes it.
- Logging the action result or an error that contains it.
- Rendering it into a cached RSC payload.

Return it only in the create/replace action's result, render it client-side from that result,
and send `Cache-Control: no-store` on these pages. Prove it in e2e:
1. Create a token and capture the secret from the panel.
2. Reload and navigate away and back: the secret is absent from the DOM.
3. The captured server stdout (as T03's e2e does) never contains the secret.
4. No URL in the browser history contains it.
5. The secret authenticates (call `authenticateBearer` from the test against the e2e database).
