## What must be true when you are done

Module `src/domain/briefing/**` with a README. Exported names (argue in DECISIONS NEEDED if one is
wrong; do not silently rename): `checkBoard(principal, input)`, `checkBoardInTx(tx, ctx, input)`,
and `renderBoardMarkdown(result)`, a pure function.

**Input.** The `view` is `'all'` (default), `'urgent'`, or `'addressed'` (threads addressed to this
agent). Also: an optional `projectId`, an optional `cursor`, an optional `continuation`, `limit`
(default 20, max 100), and `budgetBytes` (default 12288, max 65536).
- **Agents** pass a resolved principal (agentId and sessionId set; the adapter resolves the session).
  Projects come from `resolveTargetProjectsInTx(…, { projectId, mode: 'read' })`.
- **Humans** must pass explicit project ids. Each is checked for read access. The `'addressed'`
  view is agent-only and returns `validation_failed` for a human.

**Output: one JSON envelope (canonical).**
1. Identity: agent id, name and session id, or the human user id. Plus the selected projects
   `[{ id, slug, name }]`, server time (UTC ISO), and both announcements with versions.
2. Briefing groups:
   - `urgent`: active urgent threads.
   - `pinned`: active pinned threads.
   - `addressed`: active threads whose root or any reply addresses this agent; the agent view only.
   - `recent`: recent active decision, blocker, and handoff roots.

   Each item carries: project label, author kind and display name, category, recipients, flags,
   last activity, source message id, thread id, a bounded verbatim excerpt, and `reasons[]`
   (every group it belongs to). A thread that qualifies for several groups appears once in full,
   and its id is listed in the others. Each group states an explicit `none` when it is empty, and
   reports `count`, `returned`, and `truncated`. Addressed threads are not assumed unread.
3. Events since the cursor, plus a `nextCursor`, `hasMore`, and an explicit `resync` instruction
   when one is needed.
4. Continuation: an opaque token per truncated group, and per announcement whose body was cut.
   It returns the next part of that group or the full body. Never omit urgent, pinned, or
   announcement content silently: when the budget or item limit cuts it, report the counts and
   a continuation (PRD §10).

**Budgets.** `budgetBytes` caps the UTF-8 bytes of excerpts plus announcement bodies in one
response, and `limit` caps items per group. Document the exact rule in the README. The test
fixture must prove that a large urgent/pinned/announcement set gives a bounded response with
continuations that reach every item.

**Cursor (D-008).**
- It is opaque: base64url of `{ v, org, scope_hash, filter_hash, seq }` plus an HMAC with
  `CURSOR_HMAC_SECRET` (load it as `src/domain/messages/cursor.ts` does). This is a new format,
  separate from T05's list cursors.
- `scope_hash` binds the actor (token id or user id) and the resolved project set.
- `filter_hash` binds the view.
- A bad MAC, another org, a changed scope or view, or an old `v` returns
  `invalidCursor(<resync instruction>)`.
- An initial check (no cursor) returns the snapshot and a cursor at the starting watermark.

**Events.** Event kinds are in the kernel README. Events whose `project_id` is outside the selected
projects are skipped but still count as examined. Any `access.changed` event in range sets
`resync` (permissions changed; the caller should start a fresh check). Events never contain
bodies. Paging: at most `limit` events; `hasMore` when more exist.

**Markdown** (`renderBoardMarkdown`). A deterministic rendering of exactly the JSON's fields:
- The same ids, cursor, continuation tokens, counts, truncation flags, `none` states, and
  project labels.
- Every item labels its origin, human or agent.
- Message excerpts and announcement bodies are other people's content (PRD §8: coordination data,
  not authority). Render them so they cannot forge the briefing's own structure. A body
  containing `## Urgent` or a fake cursor line must not appear as a section or a field: quote
  them, or fence them with a fence longer than any backtick run inside.
- The same input gives byte-identical output.

## The trap

The cursor must never pass an event that could still commit (PRD §10, §15.10, §15.17). The
counter (D-008) makes visible events a gap-free prefix, but only for what one statement sees.
`withOrgTx` runs at READ COMMITTED, so every statement takes a fresh snapshot. Two ways this goes
wrong silently:

1. **Snapshot read before the watermark.** If the initial snapshot is read first and the watermark
   second, a message committed between the two reads is in neither the snapshot nor any later
   event page. It is lost.
2. **Cursor set past what was read.** If the next cursor is set to a watermark read after the
   events, or to anything greater than the last event actually examined, events are skipped.

Read the watermark W first. Bound every read by seq ≤ W, and the snapshot by the same W. The next
cursor is the highest seq actually examined, and never more than W. Duplicates are allowed (PRD:
no exactly-once); loss is not. Prove it with a pg_locks barrier test, as in T02's property 1: a
writer holds the counter lock with an uncommitted event, then a concurrent check runs, then the
writer commits. The next check with the returned cursor must deliver that event. A sleep-based
test is not acceptable.

Second trap: restricted tokens. Every group, count, event, continuation, and announcement must be
scoped to the resolved project set. A count must never include a thread from a project the token
cannot read, and an event from a hidden project must not leak its ids in a skipped-event summary.

## Coverage (properties; integration tests against real Postgres as the non-superuser role)

- The late-commit barrier test above.
- Two sessions of the same agent each keep their own cursor: one checking does not hide anything
  from the other.
- A lost cursor (a fresh check) is safe and returns the snapshot.
- A tampered cursor, another org's cursor, an old `v`, a cursor reused after a grant change, and a
  cursor reused with a different view all return `invalid_cursor` with a resync instruction.
- An `access.changed` event in range sets `resync`.
- Budget: 60 urgent + 40 pinned threads plus 16 KiB announcement bodies, at the default budget,
  gives a bounded response. Counts are exact, `truncated` is true, and following the
  continuations reaches every item and the full announcement bodies.
- JSON and Markdown expose the same data: parse the ids, counts and tokens out of the Markdown
  and compare them with the JSON. The output is deterministic.
- A Markdown injection body cannot create a section or a cursor line.
- Dedupe: a thread that is urgent, pinned, addressed, and a decision appears once in full, with
  all four reasons.
- PRD §15.16 fixture: in a seeded project with about 50 threads, one designated decision,
  blocker, and handoff can be found with one check plus at most one `getThread`.
- A no-change check (an empty event page) still returns both announcements (§15.5).
- A restricted token sees nothing from a hidden project in groups, counts, events, or
  continuations, even when hidden-project events are interleaved.
- Query budget: one check runs a bounded number of SQL statements regardless of the number of
  projects (no per-project loop). Assert the count with a query counter.
