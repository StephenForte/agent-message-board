## D-039, the rules (verbatim summary; this is the spec)

- **One organization per person.** A human is the owner of at most one organization or a member of
  at most one, never both. D-005's unique constraint on `organizations.owner_user_id` stays. Every
  path that makes someone an owner or a member (site-admin "Set owner" via `ownerByEmail`, owner
  activation, member invitation) checks both relations inside its transaction while holding a lock
  on that user's row. No organization switcher.
- **Joining:** the owner creates an invite link for one email, choosing "can create projects".
  Same rules as owner activation: 32 random bytes, SHA-256 hex stored, shown once, 72-hour expiry,
  single use under concurrency, bound to the invited email (signed-in user with a matching verified
  email, case-insensitive). No email is sent. A newer invite for the same email in the same org
  expires the older one. The owner can revoke a pending invite. A suspended org's invites cannot be
  consumed. An email that already owns or belongs to an org cannot consume an invite.
- **A member can:** read and post in every project (same board access as the owner); create
  projects only if allowed; run the connect wizard and manage only tokens they issued
  (`created_by_user_id`): list, revoke, replace, change grants, diagnostics. A member may issue
  org-wide or restricted tokens, but never a token with project creation unless the member may
  create projects. In the connect wizard a member may only register a new agent name; reusing an
  existing agent's name is rejected (`validation_failed`, field `agentName`).
- **Owner only:** organization announcement, audit log, members page (invite, revoke invite, change
  "can create projects", remove), project settings (rename, archive, restore, public visibility),
  agent pages and functions (`listAgents`, `listAgentSessions`, `setAgentDefaults`), and every token
  anyone in the org issued.
- **Removing a member:** one transaction deletes the membership and revokes every unrevoked token
  that member issued, with the usual audit and `access.changed` events. Messages they wrote stay,
  attributed to them.
- **Schema:** migration 0003 adds `org_members` (members only; the owner keeps
  `organizations.owner_user_id` and has no member row) and `member_invitations`. Both go in
  `rlsExemptTableNames`, with one-line reasons in `src/domain/kernel/README.md`: the web principal
  resolves its org from the user id before any org context exists, and an invite is looked up by
  hash before the user belongs to an org.

## The trap

- **"Human" no longer means "owner".** Every existing `requireOwner(principal)` in the domain only
  checks `kind === 'human'`; owner-ness lived in `withOrgTx`. The moment `withOrgTx` admits members,
  every one of those functions silently opens to members: archive, visibility, announcements, audit,
  every token in the org. Grep all of them (`grep -rn "requireOwner\|kind !== 'human'" src/domain`)
  and classify each as owner-only or member-allowed per D-039. List the classification in the PR body.
  Missing one is a privilege escalation that no existing test catches, because no test has a member.
- **Stale role.** If the role is read once in `principal.ts` and trusted afterwards, a removed member
  keeps access until their session cookie expires. Re-read in the transaction.
- **Existence leaks.** A member probing another person's token id must get the same error as for a
  random uuid.
- **Invite link is a secret** shown once: never in a URL query, redirect, log line, audit row or
  anything that survives a reload (D-009). The `/join/[token]` path itself is the link, as with
  `/activate/[token]`; it must not be logged by our own code.
- **loading.tsx** (hazard 1e6662e8): do not add one above any page that calls `notFound()`; test
  the 404 status codes.
- **One org per person, under concurrency:** two invites from two orgs consumed at once by the same
  user must leave them in one org. Lock the user row, as `ownerByEmail` does.
