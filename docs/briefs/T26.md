## The trap

1. **The revisions unique key.** `announcement_revisions_version` is unique on
   (scope, org_id, version). If it is not widened, project B's first publish inserts revision
   (project, org, 1), which collides with project A's. `insertFirst` maps *any* 23505
   (`isUniqueViolation` checks only the code) to `version_conflict`, so the owner sees "this
   announcement was updated" on a project that never had one, and can never publish there. Your
   tests must publish on two projects in one org, and two orgs, and show both reach version 1.
   Also check the same mapping cannot hide other unique violations you introduce.
2. **Grants are not RLS.** RLS isolates orgs only; per-project grants for restricted tokens are
   enforced in the domain. A batched reader that takes "all project announcements in the org" and
   filters late, or a continuation that trusts its own `projectId`, leaks an ungranted project's
   announcement to a restricted token. The continuation's project must be in the current
   selection, re-checked on every call.
3. **Org/site reads widening.** `getAnnouncementsInTx` is called by org home and every
   check_board. With project rows in the same table, an unfiltered select reads up to 16 KiB per
   project on every call, and its loop is the only thing standing between those rows and the
   result. Filter by scope in SQL.
4. **Shared test database.** `tests/integration/rls.test.ts` owns the one global site row in the
   shared vitest database (board hazard f6edeb4c). Announcement integration tests use a private
   database and non-superuser role, as `tests/integration/announcements/fixture.ts` does, dropped
   without FORCE after pg_stat_activity is empty (T06b, hazard 379035a1).

## Coverage (as properties; integration unless noted)

- Two projects in one org, and a project in a second org, each publish version 1; history and
  versions are independent per project, and independent of the org announcement.
- Concurrent first publish on one project: exactly one succeeds, the other gets `version_conflict`
  (hold the rival insert uncommitted with a barrier, as the T06 review probe did; `allSettled`
  alone resolved sequentially there). Stale `expectedVersion` writes nothing.
- Owner of org 2 passing org 1's project id: `forbidden_or_not_found`, no row, no audit. A member:
  `capability_denied`. An agent principal: `capability_denied`. Set/clear on an archived project
  succeeds.
- Restricted token granted project A only: check_board never includes B's announcement, and a
  continuation token minted for A's announcement cannot be replayed to read B (forge or edit the
  projectId → `invalid_cursor`).
- check_board with a cursor and no new events still returns the project announcement; an update
  shows on the next check; a body over the budget truncates with a continuation that reassembles
  the exact bytes; after a clear, the old continuation is `invalid_cursor` with resync.
- Query count: check_board on 1, 5 and 20 selected projects, each with a project announcement,
  adds the same fixed number of queries versus main's counts (assert the numbers).
- `getAnnouncements` still returns `{ site, org }` only, with project rows present.
- RLS with the runtime role: tenant A cannot read, insert or update tenant B's project rows; an
  inserted project row whose project belongs to another org is rejected by the FK.
- Audit payload contains no body text.
- E2E (`tests/e2e/`, new spec): owner sets a project announcement in project settings, sees it on
  the board; a stale-tab save shows the conflict and keeps the draft; clear removes the panel; a
  member sees the panel and gets 404 on project settings; hostile Markdown in the body renders
  inert (same assertion style as T09's hostile-Markdown test).
- **Migration forward on populated data:** on a database with orgs, projects, messages, a site
  and an org announcement and their revisions (seed with existing helpers on main's schema, then
  migrate to 0004), all existing rows survive unchanged and `npm run db:check` passes.

Negative controls (report each, red then restored): revisions unique key left unwidened; batched
reader not filtered by selection; continuation not re-checked against the selection; owner check
