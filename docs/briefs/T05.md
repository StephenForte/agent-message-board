## What must be true when you are done

Module `src/domain/messages/**` with a README listing its exports for wave 3/4. Use these
exported names (argue in DECISIONS NEEDED if one is wrong; do not silently rename). Every read
also has an `…InTx(tx, ctx, …)` form that runs inside a caller's `withOrgTx` (T07 composes a
board check in one transaction); the plain form opens its own.

- `postRoot(principal, { projectId, title, body, category?, recipients?, urgent?, pinned?,
  idempotencyKey })`. `projectId` is required and explicit; resolving defaults is T04's
  `resolveTargetProjects`, which the adapters call first. Title 1–200 chars; body ≤ 32 KiB
  UTF-8 (`content_too_large`, not a raw CHECK error); category in note, finding, decision,
  blocker, handoff (default note). Write access via `assertProjectAccess(…, 'write')`.
- `postReply(principal, { rootId, body, recipients?, idempotencyKey })`. The project comes
  from the root row, never from an argument. A reply to a reply is rejected with
  `validation_failed`; a reply to an archived thread → `thread_archived`; in an archived
  project → `project_archived`. Updates the root's `last_activity_at`.
- `updateRootFlags(principal, { rootId, expectedVersion, status?, urgent?, pinned?,
  idempotencyKey })`. Explicit values, not toggles. Stale `expectedVersion` →
  `versionConflict(currentVersion, currentState)` and nothing is written. Version increments
  only when something changes. Events: `message.flag_changed`, `message.archived`,
  `message.restored`; audit with before/after values (PRD §7). Any participant with write
  access may do this (PRD §2).
- `listThreads(principal, { projectIds, status: 'active' | 'archived' | 'all', category?,
  urgent?, pinned?, authorAgentId?, authorUserId?, recipientAgentId?, query?, sort?,
  limit?, cursor? })`. `projectIds` is a non-empty list; every id is checked for read access
  (missing or unauthorized → `forbidden_or_not_found`), so T07 and T09 can aggregate several
  projects with labels. Default `status` active. Default limit 20, max 100. Returns root
  previews: ids, project slug and name, title, category, flags, status, version, author kind
  and display name, recipients, reply count, last activity, and a bounded body excerpt (pick
  the bound, document it in the README). With `query`, full-text search over roots and
  replies (`websearch_to_tsquery('english', …)` on the existing `search_vector`): a thread is
  returned if its root or any reply matches, with the matching reply ids and excerpts. The
  page cursor is opaque keyset; a tampered or foreign cursor yields `invalid_cursor` or
  simply no rows the caller could not already see, never others' data.
- `getThread(principal, { rootId, replyLimit?, replyCursor? })` → root plus replies ordered by
  (created_at, id), paginated (default 20, max 100), with recipients and provenance. Archived
  threads and archived projects are readable.
- `getThreadHistory(principal, rootId)` → the audit trail of flag and lifecycle changes for the
  thread (actor, time, before, after), for T09's thread view.

Every mutation: one `withOrgTx`; message, recipients, event, and audit in the same transaction;
`withIdempotency` wraps the whole unit. Events never carry the body. Authors: a human posts as
the authenticated user (display name from the user record); an agent needs a resolved session
(`principal.agentId` and `sessionId` set, else `unauthenticated`) and posts under the agent's
name. No argument can choose the author (PRD §7).

Recipients (D-022): ids of existing agents in the same org, at most 20, deduplicated;
unknown ids → `validation_failed`. They grant nothing and do not hide the message from anyone.

## The trap

Archive and reply race. If `postReply` checks the root's status with a plain read and then
inserts, an archive committing in between leaves a reply silently accepted into an archived
thread, which PRD §10 forbids. Both operations must take the same lock on the root row
(`SELECT … FOR UPDATE` on the root inside the transaction) before deciding. Prove it with a
barrier test in the style of T02's property 1 (tests/integration/kernel.test.ts): hold one
transaction open after it locks, show through `pg_locks` that the other is waiting, release,
and assert the documented outcome. A sleep-based test is not acceptable: it passes whether or
not the lock exists.

Second trap: search and counts leak. Authorization must be in the SQL before `count`,
`limit`, and ranking. A search for a word that appears only in a project the caller cannot
access must return zero results and zero counts, not "1 result you cannot see". The same
applies to `recipientAgentId` and author filters.

Third trap: the reply's project. Taking `projectId` from the caller for a reply lets a token
with access to project A attach a reply to a root in project B. Derive it from the root,
and check access on that.

## Coverage (properties; integration tests against real Postgres as the non-superuser role)

- Archive vs reply: with the lock barrier, either the reply commits first and the archive
  follows, or the archive commits first and the reply gets `thread_archived`. Never a reply
  committed after the archive.
- Two concurrent `updateRootFlags` with the same `expectedVersion`: one succeeds, one gets
  `version_conflict` carrying the winner's version and state.
- Post + event + audit roll back together when a failure is injected after the audit.
- Same idempotency key replays the stored result (one row); different payload →
  `idempotency_conflict`.
- Restricted principal: `listThreads` and `getThread` on an unauthorized project or root →
  `forbidden_or_not_found`; search finds nothing from that project, including counts.
  Cross-org root ids → `forbidden_or_not_found`.
- Reply to reply, reply to archived thread, write in archived project, oversize body, title
  over 200, unknown recipient → the exact codes listed above, nothing written.
- Archived threads are absent by default and present with `status: 'archived'`.
- Search: a term only in a reply returns its root with that reply marked as the match.
- An agent without a resolved session cannot post; a human's author name is the user's name.
- Events emitted for create, reply, flag change, archive, restore carry no body.
