## The envelope (PRD §14) and what to measure

Envelope: 10 organizations, 100 projects per organization, 20 concurrent agent sessions per
organization (200 total), 100,000 messages and replies in total. Target: read and write p95 under
1 second, excluding client, model and network time.

1. **Seed** a private database to the envelope. Seeding may call domain functions directly or
   insert through a script; it must produce realistic shape: roots and replies mixed (about one
   reply per root on average), some urgent and pinned roots, both announcement levels set, agents
   with default assignments, a mix of org-wide and restricted tokens. Record seed time and database
   size (`pg_database_size`) after seeding.
2. **Steady run** through the real MCP endpoint of a local production build (`npm run build`,
   then `npm start` with production env as in playwright.config.ts, on ports outside 3100/3101):
   200 SDK clients (20 per org), each with its own token and session, running for 10 minutes.
   Each client loops: `check_board` (carrying its cursor), `list_messages`, `get_thread`, and
   writes (`post_message`, `reply_message`, `update_message`) at a rate that stays under D-029's
   write limit per token. Record the actual achieved calls per second, reads and writes separately.
3. **Report**, per tool: count, error count by code, p50, p95, p99 and max. Use the server's own
   `latencyMs` log lines as the primary measure (that excludes client and network time); report
   client-side timings alongside. State pass or fail against p95 < 1 s for reads and for writes.
4. **Growth**, measured as before/after counts over the steady run: `audit_records` rows (and how
   many are `agent.session_seen`), `rate_limit_windows` rows, `events` rows, `idempotency_records`
   rows, and database size. Extrapolate to rows per day at the measured call rate and say plainly
   what that means for the 10 GB staging disk.
5. **Contention**: sample `pg_stat_activity` and `pg_locks` during the run (for example every 5
   seconds) and report the maximum number of sessions waiting on a lock, and which relation. D-008
   predicts waits on `org_event_counters` during concurrent writes in one org; say whether that
   shows up and how long the waits are.
6. **Correctness under load**: zero `unavailable` errors and zero 5xx. Any `rate_limited` must come
   only from deliberate over-limit traffic, if you add any. After the run, a fresh `check_board`
   per org must still return within the budget and with a valid cursor.

Hardware caveat: this Mac is much faster than the 0.5-CPU / 512 MB web service and 0.1-CPU /
256 MB database on Render. Say so next to every latency number. The growth, contention and error
results do not depend on hardware; those are the main reason this test exists.

## The trap

A load test that measures the harness instead of the server. Two common ways: a single Node process
driving 200 clients saturates its own event loop, so client-side latencies balloon and look like a
slow server; or the harness shares one token or one session across clients, which never exercises
per-token rate limits, per-session last-seen updates or the per-org counter row the way real
agents do. Either one produces numbers that mislead the launch decision.

So: the server's own `latencyMs` lines are the primary measure; report client-side numbers only
alongside them. Give every simulated agent its own token and its own `connect_agent` session. If
the harness process is CPU-bound (check it), split it across processes.

Second trap: seeding by calling the MCP endpoint would take hours at 30 writes per minute per
token. Seed directly (domain functions or SQL inside the kernel's transaction helpers), but run
the steady phase only through MCP.
