# T18 — Data retention and throttled session-activity audit (D-033)

T15 measured about 780 bytes stored per agent call, with nothing ever deleted: every call writes
an `agent.session_seen` audit row, every write keeps a retry record (`idempotency_records`), and
rate-limit counters pile up one row per token per minute. At pilot use the 10 GB staging disk
fills in weeks. This task makes the activity audit write at most once per session per 15
minutes, and adds an hourly in-process purge of data that is past its use.

## What must be true when you are done

1. **Migration 0001** (the only number assigned to you; do not pick another). Adds
   `agent_sessions.last_seen_audited_at timestamptz` (nullable), generated with `npm run
   db:generate`. The generated SQL must contain only that change. Existing rows stay valid.
   `npm run db:check` reports no drift. If drizzle-kit wants to emit anything else, stop and report.
2. **Throttled activity audit.** In `resolveAgentSession`: `last_seen_at` on the session and the
   agent still update on every call. The `agent.session_seen` audit row is written only when
   `last_seen_audited_at` is null or at least 15 minutes old, and then that column is set in the
   same transaction. Under concurrent calls on one session, at most one row is written per window
   (use the row you already read or a conditional update; prove it with a concurrency test).
   The interval is a named exported constant.
3. **Kernel helper.** A new named export in `src/domain/kernel` (for example
   `withOrgMaintenanceTx(orgId, fn)`) that opens a transaction and sets `app.org_id` for one org,
   for system maintenance only, documented in the kernel README next to the other helpers. Do not
   reuse `withOrgBootstrapTx`: its documented purpose is organization creation.
4. **Retention module** `src/domain/retention/` with one entry point (for example
   `runRetention({ now, batchSize })`) that, for every organization:
   - deletes `idempotency_records` where `expires_at < now`;
   - deletes `rate_limit_windows` whose window ended more than one hour before `now`;
   - deletes `audit_records` with action `agent.session_seen` older than 30 days;
   - deletes in bounded batches (a named constant, for example 5,000 rows per statement), looping
     until each table is clear for that org, so no single statement holds locks for long;
   - returns per-table counts, and touches nothing else.
   It runs under one `pg_try_advisory_lock` (a fixed, documented key); if another instance holds it,
   the run is skipped and says so. A README documents the module.
5. **Hourly timer** in `src/lib/server.ts` (additive): after `listen`, schedule the first run a few
   minutes later and then hourly, with `unref()` so it never keeps the process alive. On SIGTERM or
   SIGINT, clear the timer before the existing shutdown sequence. A failed run logs one line (code
   and counts only; no SQL, rows or secrets) and never crashes the server. A successful run logs
   one line with per-table counts. Do not change anything else in server.ts.

## The trap

Two traps, both silent.

First, the purge running as the wrong context. Tenant tables have FORCE row-level security. A
DELETE without `app.org_id` set matches no rows, so a purge that forgets the helper "succeeds",
deletes nothing, and the disk still fills. Run under a superuser in tests and the same bug passes
because superusers skip RLS (D-020). So the retention tests run as the non-superuser runtime role,
seed expired rows in at least two organizations, and assert the rows are gone in both, plus a
control that unexpired rows and non-session_seen audit rows of any age remain.

Second, deleting too much. A retry record deleted early breaks the retry contract: an agent
retrying a timed-out post inside the window gets a duplicate. A current-window rate-limit row
deleted early resets the limiter. Real audit rows deleted erase provenance. So test each boundary:
an idempotency row expiring one second in the future survives and still answers a retry; the
current rate-limit window survives a purge in the middle of it; a 31-day-old `message.created`
audit row survives while a 31-day-old `agent.session_seen` row is deleted.
